# docs-context — 上下文加载器与文档同步器
管理项目文档的读与写，确保开发时有正确的上下文约束，开发后文档与代码保持同步。

## 文档路径
所有文档位于工作空间 `docs/` 目录下：
| 文档 | 路径 | 内容 |
|------|------|------|
| 架构文档 | `docs/architecture.md` | 工作空间目录结构、项目背景、项目架构、公共基础设施资源、未来规划 |
| 技术栈文档 | `docs/tech-stack.md` | 框架版本、依赖约束、环境要求、AI 代码生成限制 |
| 编码规范文档 | `docs/coding.md` | 编码规范、命名约定、API 设计规范、错误处理规范 |
| 模块注册表 | `docs/modules.md` | 各模块职责、边界、API 用途、依赖关系、影响范围 |
| 决策记录 | `docs/decisions.md` | 架构和核心决策记录（ADR） |

> 当某份文档内容非常大时，可在 `docs/` 下建子目录拆分（如 `docs/modules/payment.md`），但必须得到项目文档的owner的同意，由主文档索引指向，按需渐进加载。

## 工作模式
本 skill 有两种工作模式，根据当前任务阶段判断：

| 模式 | 触发时机 | 职责 |
|------|---------|------|
| **读模式** | 编码前 / 设计时 | 按任务类型加载对应文档，建立上下文认知 |
| **写模式** | 编码后 / 提交前 | 检查代码变更，同步更新受影响的文档 |

判断规则：
- 用户要"做什么"（写代码、改功能、修Bug、设计方案）→ **读模式**
- 用户说"做完了"（同步文档、提交前检查、功能完成）→ **写模式**
- 不确定时 → 默认 **读模式**


# 读模式：上下文加载

## 加载上下文
### 始终加载
每次触发读模式都必须加载：
- `docs/coding.md` — 编码规范是所有任务的基础约束

### 按任务类型追加加载
| 任务类型 | 额外加载 | 判断依据                                                      |
|---------|---------|-----------------------------------------------------------|
| 新增功能/模块 | architecture.md + tech-stack.md + modules.md | 新增/添加/创建/add/create/implement new 等中新建模块                  |
| 修改/优化现有功能 | modules.md + architecture.md | 修改/调整/优化/重构/update/modify/refactor/optimize，或 plan 中的改造步骤 |
| Bug 修复 | modules.md | Bug/修复/报错/异常/fix/debug/error，或 systematic-debugging 等流程中  |
| 技术选型/依赖变更 | tech-stack.md + decisions.md | 引入新库/升级版本/install/upgrade/migrate 等技术选型产出                 |
| 架构讨论/设计评审 | architecture.md + decisions.md + modules.md | 架构/方案对比/design review 等设计阶段                               |
| 接口设计/API 开发 | architecture.md + modules.md + tech-stack.md | 设计新接口/修改接口参数/联调/API design                                |

### 多类型叠加
当任务同时涉及多个类型时（如"新增模块并引入新库"），合并加载所有命中类型的文档，去重即可。

## 加载后的行为
1. 在生成代码前，确认已遵循 `coding.md` 中的所有约束
2. 涉及修改时，结合 `modules.md` 与 扫描代码 确认影响范围
3. 涉及新增时，确认不与 `modules.md` 中现有模块的职责边界冲突
4. 如果发现当前任务可能违反文档中的约束，主动提醒用户

# 写模式：文档同步

## 文档同步检查清单
根据本次代码变更内容，逐项检查。只更新涉及的文档，不涉及的跳过。
### modules.md
- [ ] 新增/删除了模块或服务 → 添加/移除模块条目
- [ ] 新增/修改/删除了 API 接口 → 更新接口描述（方法、路径、用途）
- [ ] 新增/修改了 RPC 接口 → 更新 RPC 描述和调用方说明
- [ ] 修改了模块间依赖关系 → 更新依赖描述
- [ ] 修改了模块职责或边界 → 更新职责和边界描述
- [ ] 新增/修改了 MQ Topic → 更新消息生产/消费描述
- [ ] 修改了状态枚举或状态机 → 更新枚举定义和状态流转
- [ ] 新增/修改了前端页面 → 更新前端页面与调用关系表
- [ ] 新增/修改了状态管理（Store） → 更新状态管理表
- [ ] 新增/修改了定时任务 → 更新任务清单
- [ ] 以上变更影响了其他模块 → 更新修改影响速查表

### architecture.md
- [ ] 新增/删除了服务 → 更新服务拓扑
- [ ] 修改了服务间通信方式 → 更新架构描述
- [ ] 调整了目录结构 → 更新目录结构说明
- [ ] 引入了新的基础设施组件 → 更新基础设施部分

### tech-stack.md
- [ ] 引入了新的框架/库 → 添加到技术栈列表，注明版本和用途
- [ ] 升级了框架/库版本 → 更新版本号
- [ ] 移除了框架/库 → 从列表中删除
- [ ] 变更了 AI 代码生成约束 → 更新约束部分

### coding.md
- [ ] 新增/修改了编码规范 → 更新对应章节
- [ ] 新增/修改了 API 设计规范 → 更新 API 规范章节
- [ ] 新增/修改了错误处理方式 → 更新错误处理章节
- [ ] 新增/修改了命名约定 → 更新命名章节

### decisions.md
- [ ] 做了重要的架构或技术决策 → 追加 ADR 记录
- [ ] 推翻了之前的决策 → 将旧 ADR 标记为"已替代"，新增替代 ADR

## 同步执行步骤
1. 回顾本次所有代码变更的范围
2. 按上述检查清单逐项核对
3. 对命中的条目，读取对应文档当前内容
4. 按现有文档格式和风格执行更新（保持一致性）
5. 输出同步摘要告知用户

## 文档不存在时的处理
当检测到需要更新的文档缺失时，发起根据模版创建并初始化文档流程，必须先向用户确认，禁止静默创建。

### 初始化文档流程
1. 确保 `docs/` 目录存在，不存在则创建
2. 确认用户是否允许创建缺失的文档
3. 得到用户允许后创建UTF-8文档
4. 读取模版文件内容，结合模版内容和待更新内容初始化写入文档并保存

### 文档与模版文件对应关系
| 文件                                | 对应模板                                      |
|-----------------------------------|-------------------------------------------|
| `[workspace]/docs/architecture.md`|`[skills]/assets/templates/architecture.md`|
| `[workspace]/docs/tech-stack.md`|`[skills]/assets/templates/tech-stack.md`|
| `[workspace]/docs/coding.md`|`[skills]/assets/templates/coding.md`|
| `[workspace]/docs/modules.md`|`[skills]/assets/templates/modules.md`|
| `[workspace]/docs/decisions.md`|`[skills]/assets/templates/decisions.md`|

## 同步摘要格式
完成同步后，输出以下示例格式：
```
## 文档同步摘要

本次代码变更：[简述变更内容]

### 已更新
- modules.md：[具体更新了什么]
- architecture.md：[具体更新了什么]
- XX...

### 无需更新
- tech-stack.md：技术栈未变更
- coding.md：规范未变更
- XX...

### 需要用户确认
- decisions.md：本次选择了 xxx 方案，是否需要记录 ADR？
```
