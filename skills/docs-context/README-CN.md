# docs-context

[English](README.md) | 中文

项目开发上下文加载器与文档同步器，助力上下文修正、补全和重建。

---

## 解决什么问题

在 AI 辅助开发中，项目上下文的缺失和失真是导致代码质量下降的核心原因。docs-context 通过**上下文补全与重建**方案，解决以下问题：

| 问题 | 表现 | docs-context 的应对 |
|------|------|-------------------|
| **项目持续演进下的上下文理解问题** | AI 不了解项目现状，生成的代码与项目风格、约束不一致 | 读模式：编码前按任务类型加载对应文档，建立上下文认知 |
| **架构随迭代演进逐渐失控** | 架构决策散落在代码和口头沟通中，无人维护全局视图 | architecture.md + decisions.md 持续记录架构与决策演进 |
| **跨会话/多人协作的上下文同步问题** | 换人、换会话后上下文归零，重复沟通成本高 | 5 份持久化文档作为团队共享知识库，每次会话按需加载 |
| **修改类需求的影响范围不可见** | 改一个模块不知道会影响哪些上下游 | modules.md 记录模块依赖拓扑和影响速查表 |
| **历史设计与决策不可追溯** | "当初为什么这样设计"无人能答 | decisions.md 以 ADR 格式记录决策背景、备选方案和最终选择 |
| **不同粒度的上下文混杂** | 架构级、模块级、代码级信息混在一起，找不到重点 | 5 份文档按职责分离（架构/技术栈/编码规范/模块/决策） |
| **文档、注释和代码不同步** | 文档写了不更新，逐渐变成误导 | 写模式：编码后按检查清单逐项核对，同步更新受影响的文档 |
| **长上下文衰减问题** | 一次性灌入过多上下文，AI 对关键信息的关注度下降 | 按任务类型选择性加载，只加载当前任务需要的文档 |

## 工作原理

```
编码前（读模式）                    编码后（写模式）
┌─────────────────┐              ┌─────────────────┐
│ 判断任务类型      │              │ 回顾代码变更范围   │
│       ↓         │              │       ↓         │
│ 加载对应文档      │   →  编码  →  │ 逐项检查同步清单   │
│       ↓         │              │       ↓         │
│ 建立上下文约束    │              │ 更新受影响的文档   │
└─────────────────┘              └─────────────────┘
```

## 文档体系

| 文档 | 路径 | 职责 |
|------|------|------|
| 架构文档 | `docs/architecture.md` | 目录结构、项目背景、系统架构、未来规划 |
| 技术栈文档 | `docs/tech-stack.md` | 框架版本、依赖约束、AI 代码生成限制 |
| 编码规范 | `docs/coding.md` | 编码规范、命名约定、API 设计规范、错误处理 |
| 模块注册表 | `docs/modules.md` | 模块职责、边界、API、依赖关系、影响范围 |
| 决策记录 | `docs/decisions.md` | 架构决策记录（ADR） |

所有文档均提供初始化模板，首次使用时按模板创建。
